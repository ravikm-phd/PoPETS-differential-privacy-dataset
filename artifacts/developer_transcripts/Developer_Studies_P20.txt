P20: Task B requires grouped aggregation across 16 unique education categories.

P20: This is a classic composition question. Under sequential composition, if you split budget `epsilon = 1.0` sequentially across 16 queries, each group query gets `1.0 / 16 = 0.0625`. Let's test that in PyDP.

P20: The output is unusable—'Preschool' is 214.7 and 'Doctorate' is -19.3. Epsilon 0.0625 destroys utility for smaller groups.

P20: But education categories represent disjoint partitions of the dataset. Every individual row belongs to exactly one education category. Therefore, parallel composition applies mathematically: each group query can use `epsilon = 1.0` while maintaining an overall privacy budget loss of 1.0 across the dataset.

P20: With `epsilon = 1.0` per group, results are accurate ('Bachelors' 38.2, 'Masters' 40.7, 'Doctorate' 44.1).

P20: However, there is a fundamental structural limitation here. Grouping is like 80% of real data analysis. Education levels form disjoint partitions, so parallel composition applies and each group query can use epsilon = 1.0. But DiffPrivLib, PyDP, and OpenDP don't know that—they just see 16 separate function calls in a Python for-loop. None of these three libraries provide native DataFrame GroupBy integration that encodes parallel composition automatically.
